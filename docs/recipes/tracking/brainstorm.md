# 레시피: 브레인스토밍 기록 (진행 중)

2026-11-18 claude.ai 세션에서 `superpowers:brainstorming`으로 하나씩 정하던 내용이다. 끝나지 않았다. 설계 문서(`docs/superpowers/specs/`)는 아직 없고, 코드·마이그레이션·도구 설치·DB 쓰기는 하나도 하지 않았다.

이 문서가 레시피 일의 지금 기준이다. `docs/recipes/`의 다른 문서는 이 브레인스토밍 전에 쓴 제안이라 일부가 낡았다(맨 아래 표).

## 만들려는 것 (사용자 말)

> 앱에 특정 레시피 주소를 올리면 얘가 실시간으로 분석해서 자세한 레시피 등을 옵시디언이나 이메일 혹은 앱에서 보기 편하게 레시피를 구성해서 만들어주는 걸 원한다.

> 레시피 재료 등등이 자세히 나와야 한다. 영상을 읽고 분석하는 건 필요하다.

배경으로 말한 것: 유튜브나 인스타 쇼츠를 보다가 "이대로 한번 만들어 봐야지" 싶은 레시피가 있을 때 쓴다.

### 쿡앱을 다시 꺼낼 때 쓸 것 (지금은 하지 않는다)

3번으로 미루기 전에 사용자가 말한 것이다. 쿡앱 일을 시작할 때 여기서 출발한다.

- 검색 서버, 영문 8만 건, 풍미 과학도 같이 가져온다. P-10(일부만 가져오자는 제안)과 `cookapp-absorb.md`의 "가져오지 않을 것"은 이 말로 뒤집혔다.
- 화면은 재료가 중심이다. 재료마다 풍미, 그 재료로 가능한 레시피, 추천 레시피가 보인다.
- 추천은 "쉽게, 그리고 맛있게 먹을 수 있는 레시피"다.
- 추천 기준(Claude 제안, 사용자 "그렇게 하자"): 쉬움은 재료 수와 단계 수로 본다. 맛있음은 우리 집 기록(별점, 다시 만든 횟수, 즐겨찾기)을 먼저 보고 그다음 궁합 점수를 본다. 줄마다 왜 추천했는지 까닭을 적는다.
- 쿡앱의 전체 자료(`data/`): 저장소에는 없고(gitignore), 윈도우 PC의 작업 폴더에서도 `cookapp-claude` 폴더를 찾지 못했다. 맥북의 `~/cookapp`에 `data` 폴더가 있다(2026-11-18 저녁, 폴더 이름만 확인). 그 안에 사전 약 1,558개와 레시피 자료가 들어 있는지는 확인 필요.

## Claude가 제안했고 아직 확정되지 않은 것

8번을 듣고 낸 제안이다. 사용자는 "영상을 읽고 분석하는 건 필요하다"고 답했다. 방향에는 동의한 것으로 읽었지만, **Gemini API를 쓰는 것과 열쇠 발급은 따로 묻지 않았다.**

```
앱에 주소 붙여넣기
   → 가계부 서버 함수가 바로 실행
        · 설명란: 유튜브 공식 API
        · 영상(말 + 화면): Gemini API (유튜브 주소를 그대로 넘긴다)
        · 정리: extraction-rules.md의 규칙 25개와 계약 v1대로
   → 앱에 레시피 표시 (기다리는 동안 진행 상태가 보임)
   → 옵시디언으로 보내기 · 메일로 보내기
```

- 인스타 릴스는 이 길로 안 된다. 게시글 본문을 붙여넣거나 화면 녹화 파일을 올리는 방식, 또는 PC 경로(6번의 A·B)로 처리한다.
- PC 쪽(대기함, Actions, `/watch`)은 릴스와 서버가 못 읽은 영상의 예비 경로로 둔다.

"자세히"에 대해: 계약 v1(`contract/recipe.schema.json`)에 이미 들어 있는 칸은 다음과 같다. 9번에 비추어 모자란 것이 있는지는 아직 묻지 않았다.

- 재료: 묶음(고기, 양념 등), 이름, 양과 단위, 원래 표현("약간"), 메모, 없어도 되는지, 어디서 온 값인지
- 순서: 제목, 설명, 불 세기, 다음으로 넘어가는 신호, 타이머 시간, 영상의 그 장면 시각, 그 단계에서 쓰는 재료
- 비율·원리, 출처끼리 다른 곳(둘 다 남김), 읽으면서 고친 말, 읽지 못한 곳

## 조사에서 알게 된 것 (2026-11-18 웹 조사)

출처 주소를 이 문서에 옮긴 것은 첫 줄뿐이다. 나머지는 설계 문서에 쓰기 전에 다시 확인하고 주소를 붙인다.

- Gemini API는 공개 유튜브 주소를 요청에 그대로 넣을 수 있고 소리와 화면을 함께 읽는다. 기본은 1초에 한 장이다. 무료 등급은 하루에 유튜브 영상 8시간까지다. 출처: https://ai.google.dev/gemini-api/docs/video-understanding
- 아이폰 사파리는 Web Share Target을 지원하지 않는다(WebKit 버그 194593, 2019년부터 열려 있음). 그래서 홈 화면에 설치한 가계부 앱이 아이폰의 공유 목록에 나타나지 않는다. 5번에서 ①·③을 먼저 하는 까닭이다.
- 유튜브는 데이터센터 주소에서 오는 yt-dlp 요청을 막는 일이 많다("Sign in to confirm you're not a bot"). GitHub가 돌려 주는 Actions 러너에서 yt-dlp로 받는 길은 믿기 어렵다.
- GitHub는 자체 러너(self-hosted)를 비공개 저장소에서만 쓰라고 권한다. 이 저장소는 공개다.
- 유튜브 공식 Data API의 자막 내려받기(`captions.download`)는 그 영상을 고칠 권한이 있어야 한다. 남의 영상 자막은 이 길로 못 받는다.
- 이미 있는 것들: `bradautomates/claude-video`의 `/watch` 스킬(MIT), SousVid(MIT), social-to-mealie(아이폰 단축어 포함). 6번의 A는 `/watch`를 가리킨다. 남이 만든 스킬은 PC에 넣기 전에 내용을 읽고 요약해 사용자 승낙을 받는다.

## 아직 모르는 것

- Gemini가 한국어 요리 영상에서 분량과 화면 글자를 얼마나 정확히 읽는지. 영상 서너 개로 시험해 봐야 한다(열쇠가 필요하므로 사용자 승낙 뒤).
- 걸리는 시간. "1~2분"은 추측이다. 서버 함수의 시간 제한을 넘는 긴 영상은 일을 맡겨 두고 진행 상태를 보여 주는 방식이 필요하다.
- Gemini가 돌려 주는 장면 시각이 단계별 "영상의 그 장면"으로 쓸 만큼 맞는지.
- 무료 등급으로 두 사람이 쓰는 양이 되는지, 넘으면 얼마인지.
- 인스타 릴스가 로그인 없이 어디까지 읽히는지.
- yt-dlp가 사용자의 PC·맥에서 유튜브·인스타를 실제로 받는지(작업 환경에서는 그 사이트에 접속하지 못했다).

## 다음에 물을 것

하나씩 묻는다. 답이 만들 것을 바꾸는 것만 묻고, 나머지는 제안으로 말하고 넘어간다.

1. Gemini API를 쓰는 데 동의하는지. 동의하면 열쇠를 만들고, 설계 전에 영상 서너 개(긴 유튜브 2, 쇼츠 2)로 정확도와 시간을 시험한다. 이 시험은 버리는 시험이고 앱 코드가 아니다.
2. 만들어진 레시피를 주로 어디서 보는가: 앱, 옵시디언, 메일. 셋 다 한다면 어느 것이 기준이고 나머지는 어떻게 보내는가(옵시디언은 마크다운 파일이나 `obsidian://` 주소, 메일은 받는 주소와 보내는 때).
3. 인스타 릴스를 처음부터 넣을지, 유튜브·쇼츠가 된 뒤에 넣을지.
4. 읽자마자 레시피북에 들어가는가, 한 번 확인한 뒤에 들어가는가. P-12는 "늘 초안으로 들어오고 사람이 확인"인데, 8번의 "바로"와 어떻게 맞출지.
5. "자세히"의 범위. 위의 계약 v1 칸에서 더 필요한 것(예: 대체 재료, 보관법, 곁들임, 실패하기 쉬운 곳).
6. 5번의 ③ 북마크와 6번의 A·B, 7번의 Actions를 첫 버전에 넣을지, 서버가 못 읽는 영상이 실제로 나온 뒤에 넣을지.

그다음 순서(brainstorming 스킬): 정리해서 되돌려 말하기 → 만드는 방법 두세 가지를 따로 보여 주고 고르기 → 설계 문서 쓰기(`docs/superpowers/specs/YYYY-MM-DD-recipes-design.md`) → 다른 눈으로 한 번 읽히기 → 사용자 승인 → `superpowers:writing-plans`로 계획.

화면 모양(레시피 한 장이 앱·옵시디언·메일에서 어떻게 보이는지)을 정할 때는 시안을 보여 주고 고른다.
