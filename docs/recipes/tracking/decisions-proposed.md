# 레시피: 제안 결정

2026-11-18 claude.ai에서 만든 제안이다. 사용자가 정하면 저장소 결정 기록(`docs/grocery/tracking/decisions/index.md`)에 다음 번호로 옮기고 이 파일에서 지운다. 공개 저장소의 main에서 본 마지막 번호는 D-055였다(로컬이 더 앞서 있을 수 있다).

## 2026-11-18 브레인스토밍 뒤의 상태

같은 날 브레인스토밍에서 사용자가 아래를 정했다. 자세한 내용과 사용자 말은 `brainstorm.md`에 있다. 저장소 결정 기록(`docs/grocery/tracking/decisions/index.md`)에는 아직 옮기지 않았다. 설계 문서가 승인될 때 번호를 붙여 옮긴다.

| 제안 | 상태 |
|---|---|
| P-01 | **확정.** 가계부 앱에 합친다 |
| P-02 | **다시 검토.** 사용자는 앱에 주소를 올리면 바로 분석되기를 원한다. 서버 함수가 읽는 구조를 제안했고 확정 전이다 |
| P-07 | **다시 검토.** 영상을 읽고 분석하는 것(말과 화면)이 필요하다고 했다. Gemini API를 기본으로 쓸지는 아직 묻지 않았다 |
| P-10 | **뒤집힘, 그리고 미룸.** 쿡앱은 나중에 하되, 할 때는 검색 서버·영문 8만 건·풍미 과학도 가져온다 |
| P-11 | **뒤집힘.** 아래 탭에 '레시피' 탭을 따로 만든다 |
| P-03, P-05, P-06, P-09 | 사용자가 따로 말하지 않았다. 제안 그대로 |
| P-04, P-08, P-12 | 구조가 바뀌면 같이 바뀐다. 설계에서 다시 본다 |

## 처음 제안 (브레인스토밍 전)

| 번호 | 제안 | 까닭 | 다른 길 |
|---|---|---|---|
| P-01 | 레시피는 가계부 저장소 안의 한 부분으로 만든다: `src/recipes/`, `tests/recipes/`, DB 스키마 `recipe`, 문서 `docs/recipes/`. | 장보기를 합친 판단(D-010)과 같다. 계정·가구·디자인·배포를 그대로 쓰고, 장보기 목록·영수증 품목과 바로 이어진다. | 새 저장소(장보기를 처음 만들 때처럼). 나중에 다시 합쳐야 한다. |
| P-02 | 영상과 글을 읽는 일은 앱 서버가 아니라 Claude Code와 claude.ai가 한다. 앱은 결과만 받는다. | 영상 사이트는 서버에서 읽기 어렵고 비공식 접근이 앱 운영에 묻는다. 두 사람이 쓰는 양은 구독 안에서 된다. | 앱 서버 함수가 자막을 받고 Claude API로 정리(레시피마다 요금, 막힐 위험). |
| P-03 | 등록 자료의 모양은 `contract/recipe.schema.json` v1 하나다. 두 스킬, DB 함수, 앱 타입이 이것을 따른다. | 두 곳에서 담아도 같은 모양. | — |
| P-04 | 등록은 `recipe.import_recipe()` 하나로만 한다. Claude가 Supabase MCP·커넥터로 `recipe` 표에 직접 쓰지 않는다(대기함은 R1에서 함수로 감쌀지 정한다). 부르기 전에 요약을 보여 준다. | 운영 DB에 Claude가 쓰는 길을 하나로 좁힌다. 가계부의 "가계부 내역에 쓰는 것은 함수 하나로만"과 같은 생각. | Claude는 JSON 파일만 만들고, 사용자가 앱의 "가져오기"에 붙여 넣는다(Claude가 DB에 쓰지 않음, 한 단계 더 번거로움). |
| P-05 | 숫자(분량·인분·시간)는 작성자의 글, 화면, 자막·받아쓰기에서만 온다. 2차 자료와 덧붙임은 숫자의 출처가 아니다. 출처끼리 다르면 둘 다 남긴다. | 가계부·장보기의 "숫자는 출처가 있는 값만"을 레시피에 옮긴 것. 세 도우미 비교에서 실제로 섞였다. | — |
| P-06 | 자막·받아쓰기 원문과 영상·음성 파일은 저장소와 DB에 넣지 않는다. `.recipe-cache/`에만 두고 읽은 뒤 지운다. 단계는 다시 쓴 글과 영상 시각으로 남긴다. | 저장소가 공개다. 원본을 대신하지 않는다. | DB에 자막 보관(다시 정리할 때 편하지만 필요하면 다시 받으면 된다). |
| P-07 | 화면 글자가 꼭 필요한 영상은 먼저 장면 몇 장을 Claude Code가 읽는다. Gemini API(영상 전체 이해)는 R6에서 3개 영상으로 비교한 뒤 쓸지 정한다. | 구독 안에서 되는 길이 먼저. Gemini는 키와 비용이 따로 든다. | 처음부터 Gemini API를 L3 기본으로. |
| P-08 | claude.ai에서 자막을 읽는 길은 내장 브라우저(데스크톱 앱이 켜져 있을 때)를 기본으로 하고, 안 되면 대기함에 넣는다. 외부 자막 도구(TubeAlfred, Firecrawl, 자막 MCP 서버)는 R5에서 휴대폰 사용이 불편하면 그때 하나만 고른다. | 지금 되는 길이 있고, 외부 도구는 계정·키·한도가 따로다. | 지금 하나를 골라 연결. |
| P-09 | 인스타그램은 본계정 쿠키를 쓰지 않는다. 로그인 없이 되는 범위와 "파일로 넣기"(저장한 영상 + 게시글 본문)를 기본으로 한다. 쿠키가 꼭 필요하면 따로 만든 계정의 쿠키를 저장소 밖에 둔다. | 쿠키는 계정 열쇠다. 자동 접근으로 계정이 제한될 수 있다. | 인스타는 글 붙여넣기만 지원. |
| P-10 | 쿡앱은 통째로 옮기지 않는다. 불변식, 재료 사전(한식 위주), 재료 줄 파서, 겹침 순위, 있음/사야 함 대조, 분류 낱말을 가져오고 검색 서버·영문 8만 건·풍미 과학은 가져오지 않는다(`cookapp-absorb.md`). | 쿡앱은 운영할 것이 많아 멈췄다(추측). 목표는 Postgres와 우리 레시피만으로 된다. | 쿡앱을 따로 배포해 링크로 잇기. |
| P-11 | 레시피의 자리: 아래 탭 줄에 '레시피'를 더하지 않고 **장보기 탭 안의 전환**(목록 \| 시세 \| 레시피)이나 '알아보기' 옆으로 두는 쪽을 먼저 검토한다. R3 설계에서 시안을 보고 정한다. | 탭이 이미 여덟 개다(우리집, 내역, 장보기, 통계, 고정 지출, 알아보기, 함께 기억할 것, 설정). 레시피는 장보기와 가장 가깝다. | 새 탭 '레시피'. 찾기는 쉽지만 탭 줄이 더 붐빈다. |
| P-12 | 새 레시피는 늘 초안(`draft`)으로 들어오고, 사람이 검토해야 레시피북(`saved`)에 들어간다. 확인이 필요한 곳이 0이어도 그렇다. | 자동 자막과 정리에는 오류가 있다. 두 사람이 믿고 쓰려면 한 번은 본다. | 확인 필요가 0이면 바로 저장. |

## 정해야 하지만 제안이 없는 것

| 물음 | 정할 때 |
|---|---|
| 받아쓰기를 돌릴 컴퓨터(윈도우 PC, 맥북)와 모델 크기 | R0에서 사양 확인 뒤 |
| 공공 한식 레시피 4천 건을 넣을지 | R7을 써 본 뒤 |
| 가진 재료에 양(몇 g 남았는지)까지 적을지. 제안 없이 "있음/없음"만으로 시작한다 | R7 설계 |
| 요리 기록을 가계부의 다른 기록(함께 기억할 것, 달력)과 이을지 | R7 뒤 |
