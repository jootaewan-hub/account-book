# 레시피 탭: 영상 주소를 레시피로

## 요청

> 앱에 특정 레시피 주소를 올리면 얘가 실시간으로 분석해서 자세한 레시피 등을 옵시디언이나 이메일 혹은 앱에서 보기 편하게 레시피를 구성해서 만들어주는 걸 원한다. (사용자, 2026-11-18)

유튜브나 쇼츠를 보다가 "이대로 한번 만들어 봐야지" 싶은 레시피를, 영상을 다시 보지 않아도 따라 할 수 있는 레시피로 바꿔 두 사람이 보관한다. 2026-11-18(claude.ai)과 2026-11-19(맥의 Claude Code)에 하나씩 정했다. 사용자의 말과 결정 순서는 `docs/recipes/tracking/brainstorm.md`의 1~19번에 있다. 이 문서의 "(N번)"은 그 번호다.

A1이나 A2가 안 되면 오른쪽 길로 바로 가지 않고 **멈추고 사용자에게 묻는다.** 두 길 모두 새 키·요금이 생기거나 근거가 맥 밖으로 나가서, 사용자가 그때 정할 일이다.

## 진행 순서와 승인 지점

- 네 조각을 모두 로컬에서 만들고 시험한다: DB는 PGlite, 서버 함수는 처리 함수 시험, 처리기는 서버 대신 파일로 결과를 내는 "건조 실행"으로 실제 영상(A1~A5)을 돌린다. 그래서 수집·검증의 문제는 앞에서 드러난다.
- 되돌리기 어려운 일은 끝에 한 번에 묻는다(이 저장소에서 해 온 방식): 공유 DB 마이그레이션 적용, `recipe-worker` 배포와 `RECIPE_WORKER_SECRET`, Exposed schemas에 `recipe` 더하기, 처리기 설치·launchd 등록, 구글 OAuth 허락, main 병합(배포). 그 뒤 실제 맥 → 서버 → 앱으로 끝까지 한 번 돈다.
- main에는 한 번에 올린다(배우자가 반쯤 된 탭을 보지 않게). 버전은 그때의 main을 보고 가운데 숫자를 올린다(D-028).

## 사용량

- 하루 10개쯤 담을 예정이다(21번). 구독에서 처리기가 쓰는 양에 하루 한도를 둔다(처음값: 하루 레시피 15개, 설정에서 바꿈). 한도에 닿거나 Claude가 사용량 제한으로 거절하면 그 일은 실패가 아니라 대기로 돌아가고, 제한이 풀린 뒤 다시 한다. 사용량 제한으로 다시 하는 것은 "세 번까지"에 세지 않는다.
- A2에서 레시피 하나에 드는 양을 재어 이 한도와 장면 수(24장)·다른 곳 가리기(8번)를 맞춘다. 정리에 쓸 모델도 그때 정한다.

## 만드는 방법 (고른 것과 버린 것)

| 방법 | 내용 | 결과 |
|---|---|---|
| **가. 맥의 우리 수집기 중심** | 맥이 설명란·자막을 받고, 자막이 없으면 whisper.cpp로 받아쓰고, 1초에 한 장 장면을 뽑아 macOS 글자 인식으로 화면 글자를 시각과 함께 뽑는다. Claude가 이 근거로 정리·검증한다. `/watch` 스킬은 자동 처리가 못 한 영상을 Claude Code에서 손으로 다시 볼 때 쓰는 예비로 설치한다. | **고름(17번).** 화면 글자를 1초 간격으로 훑어 쇼츠의 약점을 메우고, 근거가 처음부터 출처·시각을 단 우리 형식이다. 영상·소리는 맥 밖으로 나가지 않는다. 대신 수집 스크립트를 만들고 고쳐야 한다 |
| 나. `/watch` 중심 | 처리할 때마다 `/watch`가 받고·자막·장면 그림(장면 바뀜 기준 최대 100장)을 맡고 Claude가 그림을 본다 | 안 고름. 질문에 답하는 도구라 우리 형식으로 다시 맞춰야 하고, 그림 100장은 사용량이 크고, 화면 글자를 따로 읽지 않는다. 받아쓰기는 WhisperX(약 3GB)나 외부 서비스로 소리를 보내야 한다 |
| 다. 서버 함수 + Gemini | 앱에 붙여넣으면 가계부 서버 함수가 Gemini에 유튜브 주소를 넘겨 바로 읽는다 | 안 고름(10번). 맥이 하루 약 20시간 켜져 있어 맥으로 충분하다. Gemini는 새 키와 약관(무료는 보낸 내용을 Google이 쓰고 사람이 읽을 수 있음)이 따른다. A1이 안 되면 다시 꺼낸다 |
| 라. claude.ai·Claude Code에서 손으로 | 사람이 Claude에게 주소를 주고 등록시킨다(처음 제안 P-02, `claude-ai-workflow.md`) | 안 고름. 붙여넣으면 알아서 되기를 원했다(7·8번) |

서버만으로 하지 않는 까닭: 유튜브는 데이터센터에서 오는 내려받기를 자주 막고, 가계부 서버 함수에서는 yt-dlp·ffmpeg·받아쓰기를 돌릴 수 없고, 가계부가 쓰는 Claude API는 영상을 받지 않는다. 서버의 Claude는 로그인한 사용자의 토큰으로 부르는 방식(D-009)이라 사람 없이 도는 일에서는 쓸 수 없다. GitHub Actions 러너도 데이터센터라 유튜브가 막는다.

## 전체 흐름

```
휴대폰 앱에 붙여넣기 / 맥·PC 북마크(?tab=recipes&add=주소)
  → recipe.inbox 에 한 줄 (대기)
  → 맥 처리기가 서버 함수 recipe-worker 로 일을 받음 (맥이 꺼져 있거나 잠들면 대기)
      1 수집   설명란·자막 → (없으면) 받아쓰기 → 장면·화면 글자
      2 정리   Claude: 근거 → 레시피(계약 v2)
      3 검증   기계 검사 → 두 번째 읽기 → 다른 곳 맞춰 고치기 → 남은 것은 "확인 필요"
      4 등록   recipe-worker 가 검사하고 recipe.import_recipe 로 넣음
  → 앱: 확인 필요가 없으면 레시피북, 있으면 "확인 필요"
  → 레시피북에 들어간 것은 맥이 구글 드라이브·옵시디언에 씀 (앱에서 고치면 다시 씀)
```

## 1. 담기

- 레시피 탭 맨 위에 주소 칸 하나. 붙여넣고 "담기".
- 받는 주소: `youtube.com/watch?v=`, `youtube.com/shorts/`, `youtu.be/`, `m.youtube.com`. 출처 열쇠 `youtube:<영상 id>`로 정규화한다(쇼츠도 같은 id). 다른 주소는 "지금은 유튜브 영상과 쇼츠만 담을 수 있어요".
- 같은 출처가 이미 레시피북에 있으면 담지 않고 그 레시피를 연다. 대기·처리 중이면 그 줄을 보인다.
- 북마크: `https://<앱 주소>/?tab=recipes&add=<인코딩한 주소>`를 여는 북마크릿. 앱은 `add`를 읽어 "이 영상을 담을까요?"를 보이고 한 번 눌러야 담는다. 남이 보낸 링크로 일이 쌓이지 않게 하려는 것이다. PC 브라우저에서 앱에 로그인해 두어야 한다(로그인은 이메일·비밀번호). 지금 `?tab=`은 `grocery`만 받는다(`App.tsx:111-116`). `recipes`를 더한다.
- 담기는 로그인한 구성원이 앱에서만 한다(RLS: 자기 가구, `added_by` = 본인).

## 2. 맥 처리기

### 어디서, 어떻게 도는가

- 코드는 이 저장소 `tools/recipe-worker/`(TypeScript, Node. 앱의 계약 검사 코드를 같이 쓴다). 실행은 저장소가 아니라 **설치한 사본**에서 한다. 이 저장소는 브랜치가 자주 바뀐다. 설치 스크립트가 정한 커밋을 `~/Library/Application Support/recipe-worker/`에 만들고 launchd 사용자 에이전트(로그인할 때 시작, 죽으면 다시 시작)로 띄운다.
- 비밀은 `~/.config/recipe-worker/`(권한 600): 처리기 비밀 문자열, 구글 갱신 토큰. 로그에 쓰지 않는다.
- 작업 파일(영상·소리·장면·자막)은 `~/Library/Caches/recipe-worker/<일 id>/`. 일이 끝나면 지운다. 실패한 일은 원인을 보려고 하루 두었다가 지운다. 저장소의 `.recipe-cache/`는 손으로 하는 시험에만 쓴다.
- 일 받기: 처리기가 20초마다 `recipe-worker`에 "일 있나"를 묻는다(Realtime 대신. 사람 없이 도는 쪽은 단순한 쪽이 낫다). 하루 4,300번쯤이다. 처리 중에는 30초마다 진행 단계를 알린다. 진행 알림이 3분 끊기면 다른 실행이 다시 가져갈 수 있다(장보기 `item_searches`의 방식). 한 일은 세 번까지 다시 한다.
- 잠: 이 맥은 "1분 쉬면 잠자기"로 설정되어 있다. 처리기는 일하는 동안 `caffeinate -i`로 잠을 막는다. 사용자가 말한 켜진 시간(08:30~18:20, 20:00~06:30)에는 일이 없어도 잠을 막아 대기함을 볼 수 있게 한다. 시간은 설정 파일에서 바꾼다. 뚜껑을 닫으면 잠들고, 그동안 일은 기다린다.
- 처리기는 살아 있다는 표시(마지막 확인 시각, 버전)를 남긴다. 앱은 대기 중인 일 옆에 "맥 처리기 마지막 확인: 3분 전"을 보인다. 오래 끊겨 있으면 "맥이 켜지면 처리돼요".
- 도구 갱신: yt-dlp는 유튜브가 바뀌면 자주 고쳐진다. 처리기는 하루 한 번 `brew upgrade yt-dlp`를 돌린다. 받기에 실패하면 한 번 갱신하고 다시 해 본다.

### 수집 (L0~L3, `docs/recipes/ingest-sources.md`)

1. **영상 정보·설명란(L0):** `yt-dlp -J --skip-download`. 제목, 채널, 올린 날, 길이, 설명란, 챕터, 자막 목록. 60분이 넘는 영상은 받지 않는다("영상이 너무 길어요"). 비공개·연령 제한·지역 제한은 그 까닭으로 실패 처리한다. 막히면 우회하지 않는다.
2. **자막(L1):** 작성자 한국어 자막, 없으면 자동 자막(json3, 시각 포함).
3. **받아쓰기(L2):** 한국어 자막이 없으면 소리만 받아 whisper.cpp로 받아쓴다. 설명란에서 뽑은 재료 이름을 처음 말(prompt)로 준다.
4. **화면(L3):** 720p 이하 영상을 받아 1초에 한 장씩 뽑고, 앞 장과 거의 같은 장은 버린다. 남은 장마다 macOS 글자 인식(작은 Swift 도구, `ko-KR`·`en-US`)으로 글자 줄과 시각을 뽑는다. Claude에게 보일 장면은 숫자·단위·재료 이름이 보이는 장과 장면이 바뀐 곳에서 24장 안쪽으로 고른다.
5. 근거 묶음(`evidence.json`): 정보, 설명란, 자막·받아쓰기 조각(시작 초), 화면 글자 줄(초), 고른 장면 목록. 작업 폴더에만 둔다.

### 정리 (첫 번째 읽기)

- `claude -p`에 근거, 정리 규칙(`extraction-rules.md`를 이 설계에 맞게 고친 판), 계약 v2를 주고 JSON 하나를 받는다. 도구는 그 일의 작업 폴더 안 파일 읽기만 허락한다(장면 그림을 보려고). 셸·쓰기·웹은 막는다.
- 결과는 계약 v2로 검사하고, 틀리면 틀린 곳을 알려 한 번 더 시킨다. 그래도 틀리면 실패.
- 숫자를 쓴 재료는 출처(설명란, 작성자 자막, 자동 자막, 받아쓰기, 화면)와 그 숫자가 나온 시각(설명란 제외)을 단다.
- 같은 읽기에서 분류, 덧붙인 분량, 용어 풀이, 재료 사전 후보도 만든다(아래 4~6). 난이도는 코드가 규칙으로 계산한다.

### 검증 (12번, "검증·비교해서 적절하게 수정")

맥이 비교해서 고칠 수 있는 것은 스스로 고치고, 고친 내역을 남기고, 판단이 안 서는 것만 사람에게 보인다. 모델에게 맡기기 전에 코드가 먼저 막는다. 두 번 읽어도 같은 실수를 할 수 있기 때문이다.

**V1 기계 검사(코드):**

- **숫자는 근거에 글자로 있어야 한다.** 분량마다 그 출처의 글에서 재료 이름 가까이에 그 숫자가 있는지 찾는다. 설명란은 같은 줄, 자막·받아쓰기는 단 시각 ±10초의 조각, 화면은 단 시각 ±3초의 글자 줄이다. 한국어 수(한·두·세·네…, 반), 분수(1/2, ½), T·t 표기를 같은 꼴로 바꿔 비교한다.
  - 단 출처에 없고 다른 출처에 있으면 출처와 시각을 고친다(고친 곳에 남김).
  - 어디에도 없으면 숫자를 지우고("약간" 같은 원래 표현은 남김) "확인 필요: 출처에서 숫자를 찾지 못함". 모델에게 숫자를 다시 만들게 하지 않는다.
- 인분·시간도 같다.
- 단위 검사(아래 "단위").
- 단계에 나온 재료가 재료 목록에 있다. 없으면 목록에 넣는다(고친 곳). 필수 재료가 어느 단계에도 안 쓰이면 확인 필요.
- 단계 시각은 영상 길이 안에 있다.
- 분류 말은 정해진 낱말 안에 있다.

**V2 두 번째 읽기:** 첫 결과를 보여 주지 않고 다른 방법으로 다시 읽는다. 첫 번째가 글자(설명란·자막·화면 글자) 위주였으면 두 번째는 장면 그림과 자막을 먼저 본다. 재료 이름·분량·단위·시각만 뽑게 한다. 둘을 이름으로 짝지어 다른 곳을 찾는다.

**V3 다른 곳 가리기:** 다른 곳마다 그 시각 앞뒤의 근거(자막 ±15초, 화면 글자 ±5초, 장면 3장 안쪽)만 주고 "근거에 있는 값 중 어느 것인가, 또는 모름"을 고르게 한다. 고른 값이 근거에 글자로 있는지 코드가 다시 본다. 있으면 고치고, 없거나 "모름"이면 확인 필요로 둔다. 레시피 하나에 이렇게 묻는 것은 8번까지만 하고, 나머지는 확인 필요로 넘긴다(사용량이 한 영상에 몰리지 않게).

**V4 출처끼리 다를 때:** 설명란과 영상이 다르게 말하면(예: 설명란 "약불", 영상 말 "중불") 설명란 값을 기본으로 하되 다른 쪽을 지우지 않고 "다른 곳"에 둘 다 남긴다(R-04). 이것도 확인 필요로 센다.

**남기는 것:**

- 고친 곳: 무엇을(재료 3번 분량 등), 전, 후, 근거(출처와 시각), 방법(규칙·비교). 자막 원문은 남기지 않는다(P-06).
- 확인 필요: 무엇, 후보 값들(값, 출처, 시각), 까닭.
- 확인 필요가 하나도 없으면 레시피북에 바로 들어간다. 있으면 레시피북에 "확인 필요"로 보이고, 사람이 다 보면 "확인을 마침"이 된다.

## 3. 단위 (15번)

- 적기: 출처 표기 그대로("2T", "2스푼", "1/2개", "한 줌"). ml로 바꿔 쓰지 않는다.
- 단위 표(코드): 큰술(T) 15ml, 작은술(t) 5ml(사용자 말). 컵, 종이컵 같은 나머지 기준값은 공식 출처를 찾아 주소와 함께 단위 표에 적는다(확인 필요). g·개·대·모·장·줌·꼬집처럼 부피가 아닌 단위에는 ml를 붙이지 않는다.
- 계량 도구: 레시피마다 "계량스푼 / 밥숟가락 / 섞어 씀 / 확인 못 함"과 그 근거(말·화면의 시각, 설명란)를 둔다. "계량스푼", "밥숟가락", "종이컵" 같은 말과 장면 속 도구로 정한다.
  - 계량스푼이면 화면에 "2큰술 (30ml)"처럼 보인다.
  - 밥숟가락이면 "2큰술 · 밥숟가락 기준"으로 보이고 ml는 붙이지 않는다.
  - 확인 못 하면 "2큰술"만 보이고 레시피 머리에 "계량 도구 확인 못 함"을 적는다. 레시피마다 확인 필요가 쏟아지지 않게, 확인 필요로 올리는 것은 "스푼"·"숟가락"처럼 어느 쪽인지 정하지 않은 표기가 분량에 쓰였을 때만이다.
- 헷갈리기 쉬운 것은 V1에서 따로 본다: T와 t(설명란·화면 글자의 대소문자를 그대로 비교), "스푼"·"숟가락", "컵", 분수와 "반 개".

## 4. 분류 (18·23번)

| 기준 | 낱말 | 개수 |
|---|---|---|
| 요리 종류 | 한식, 양식, 일식, 중식, 기타 (23번. 계약 v1의 16개를 이 다섯으로 줄인다) | 1 |
| 주재료 | 돼지고기, 소고기, 닭고기, 기타 육류, 해산물, 달걀, 두부·콩, 채소, 버섯, 면, 밥·곡물, 빵·밀가루, 유제품, 기타 (계약 v1과 같음) | 1~3 |
| 세부 재료 | 그 레시피 재료 목록에 있는 이름(앞다리살, 느타리버섯 등). 재료 목록에 없는 말은 못 쓴다 | 1~3 |
| 조리법 | 볶음, 구이, 조림, 찜, 국·탕, 찌개·전골, 튀김, 무침, 부침·전, 비빔, 샐러드, 오븐, 끓이기, 기타 | 1~3 |
| 난이도 | 쉬움, 보통, 어려움 (23번) | 1 |
| 상황 | 반찬, 한그릇, 국물, 술안주, 손님상, 도시락, 간식·디저트, 아침, 소스·양념 | 0~4 |

- 정리할 때 붙이고 V1이 낱말을 검사한다. 앱에서 고치면 드라이브·옵시디언의 자리도 옮긴다.
- **난이도는 규칙으로 정한다**(모델의 느낌이 아니라, 왜 그런지 보이게). 필수 재료 수(8개 이하 0점, 9~14개 1점, 15개 이상 2점), 단계 수(6개 이하 0점, 7~11개 1점, 12개 이상 2점), 손이 많이 가는 조리법(튀김, 반죽, 오븐이 있으면 1점)을 더해 0~1점 쉬움, 2~3점 보통, 4점 이상 어려움. 상세에 "재료 15 · 단계 12 → 어려움"처럼 근거를 보이고, 앱에서 바꿀 수 있다(바꾸면 출처 `user`). 점수 경계는 실제 레시피 몇 개를 넣어 본 뒤 구현자가 고칠 수 있다.
- 폴더는 `레시피/<요리 종류>/<첫 주재료>/<첫 조리법>/<난이도>/`(23번). 여러 기준으로 함께 거르는 일은 드라이브의 목록 표와 앱에서 한다.
- 파일 이름: `<요리 이름> (<채널>)`. 같은 이름이 있으면 뒤에 짧은 출처 id를 붙인다.

## 5. 덧붙임, 용어 풀이, 인분 바꾸기 (22번)

영상에서 온 값은 영상 그대로 적고(15번), 요리하기 쉽게 덧붙이는 값은 따로 담아 늘 구별해 보인다(R-07). 덧붙인 값은 다른 색·작은 글자에 "덧붙임"을 달고, 출처 숫자 칸에는 들어갈 수 없다(DB 제약, R-01).

- **덧붙인 분량:** 출처가 "약간"·"적당히"처럼 숫자를 주지 않은 재료에만 붙인다. 출처 숫자가 있는 재료에는 붙이지 않는다. 화면: "약간 · 덧붙임 1작은술쯤". 출처에 인분이 없으면 덧붙인 인분("덧붙임 2인분쯤")을 둔다.
- **용어 풀이:** 레시피에 나온 요리 말(한소끔, 자작하게, 깍둑썰기)과 낯선 재료(참치액, 미림)에 한두 문장 풀이를 둔다. 영상이 직접 풀어 주었으면 그 출처와 시각, 아니면 "덧붙임". 재료·단계 글에서 그 말에 밑줄을 긋고 누르면 풀이가 뜬다. 레시피 하나에 10개까지.
- **판단 기준:** 영상이 넘어가는 신호를 주지 않은 단계에 덧붙인 기준(계약 v1의 `editor_tip`)도 같은 표시로 따로 둔다.
- **인분 바꾸기:** 상세와 요리 화면에서 1인분부터 8인분까지 고른다(24번). 기준 인분은 출처에 인분이 있으면 그 값, 없으면 덧붙인 인분이고, 이때는 "기준 2인분(덧붙임, 영상에 인분 없음)"처럼 밝힌다. 숫자 분량에 (고른 인분 ÷ 기준 인분)을 곱하고 "원래 2큰술 → 4큰술"처럼 원래 값을 함께 보인다. g·ml는 정수로, 큰술·작은술·개 같은 단위는 ¼ 단위 분수(½, ¼, ¾)로 반올림해 보인다. "약간"·"한 줌"은 그대로 두고, 덧붙인 분량은 곱하되 "덧붙임" 표시를 지킨다. 계산은 화면에서만 하고 저장하지 않는다. 사본(드라이브·옵시디언)은 영상 기준 분량이다.
- **검증에서:** V1은 덧붙인 값이 출처 숫자 칸에 들어가지 않았는지, 영상 출처를 단 용어 풀이의 말이 그 시각 근거에 실제로 있는지 본다. 덧붙인 분량 자체는 근거와 맞춰 볼 대상이 아니다(근거가 없어서 덧붙인 것이므로).

## 6. 가진 재료와 장보기 (22번)

- **재료 표준 사전**(`recipe.ingredient_dict`, 쿡앱 형식): 레시피 재료를 사전 항목에 맞춰야 가진 재료와 비교할 수 있다. 쿡앱 사전 가져오기는 뒤로 미뤘으므로(3번) 사전은 비어서 시작해 레시피가 들어올 때마다 늘린다. 처리기가 재료마다 이름·동의어가 정확히 맞는 항목을 찾고, 없으면 새 항목(출처 `added`)을 만들어 `recipe-worker`가 넣는다. 애매하면 비우고 확인 필요로 둔다(R-13). 나중에 쿡앱 사전을 가져오면 합친다.
- **가진 재료**(`recipe.pantry`, 가구마다): "지금 있음"과 "늘 있음"(소금·설탕·간장처럼 한 번 정하면 계속 있음). 넣는 길:
  - 레시피 탭의 "가진 재료" 화면에서 찾아 고르기.
  - 레시피 상세의 재료 옆 체크.
  - 장보기에서 "샀음"으로 표시된 품목 가운데 사전에 맞는 것을 "가진 재료에 넣을까요?"로 보여 준다. 한 번 눌러야 넣는다(자동으로 넣지 않음). 장보기 표는 읽기만 한다.
  - 다 쓴 것은 사람이 끈다. 요리 화면 끝에 "다 쓴 재료 끄기" 목록을 둔다.
- **레시피에서:** 재료마다 있음·없음, 머리에 "가진 재료 9/14". 레시피북 거르기에 "지금 만들 수 있음"(모자란 필수 재료 0)과 "1~2개만 사면 됨"(`recipe.cookable()`). 없어도 되는 재료(`optional`)와 "늘 있음"은 모자람에 세지 않는다.
- **장보기 목록에 담기:** 상세의 "모자란 재료 장보기에 담기" → 모자란 필수 재료 목록(체크로 뺄 수 있음, 이미 장보기 목록에 있으면 "이미 있음"으로 빼 둠) → 담기. 앱이 로그인한 구성원으로 `grocery.items`에 넣는다. 장보기의 RLS와 제약(이름 60자, 담은 사람 본인)을 그대로 따른다. 장보기 분류(정육, 수산, 채소, 과일, 유제품, 계란, 가공, 냉동, 음료, 생활용품, 기타)는 사전 대분류에 정해 둔 짝으로 고른다(육류→정육, 수산물→수산, 채소·버섯→채소, 유제품·난류→유제품 또는 계란, 장·양념·소스→가공, 모르면 기타). 레시피 분량은 사는 단위와 달라서 장보기 품목의 규격 칸은 비운다.
- **경계:** `recipe` 쪽 함수와 마이그레이션은 `grocery`에 쓰지 않는다. 장보기로 가는 길은 앱의 로그인한 사용자 한 길뿐이다(D-003과 같은 생각).

## 7. 보관: 구글 드라이브와 옵시디언 (13·18·19번)

- 원본은 앱(DB)이다. 드라이브와 옵시디언은 보관 사본이다. **확인을 마친 레시피만** 쓴다. 앱에서 고치면(내용·분류·메모) 다시 쓰고, 분류가 바뀌면 옮긴다. 사본에서 고친 것은 앱으로 돌아오지 않는다. 사본 맨 위에 "앱에서 고치면 이 파일은 다시 써져요"를 적는다.
- 앱에서 지우면 드라이브는 휴지통으로, 옵시디언은 보관함의 `.trash`로 옮긴다. 둘 다 되살릴 수 있다.
- 사본에 들어가는 것: 제목, 출처 영상 주소, 채널, 올린 날, 저장한 날, 분류, 난이도와 근거, 계량 도구, 재료(묶음별, 원래 표기, 출처와 시각 링크, 덧붙인 분량은 "덧붙임"으로 따로), 용어 풀이, 순서(불, 넘어가는 신호, 시각 링크 `…&t=242s`), 원리, 다른 곳, 고친 곳, 우리 집 메모·별점. 인분 바꾸기는 앱에서만 한다(사본은 영상 기준 분량).
- **구글 드라이브:** 내 드라이브의 `레시피` 폴더 아래 위 폴더 구조로 레시피마다 구글 문서 하나를 둔다. HTML로 만들어 올리면서 구글 문서로 바꾼다. `레시피 목록` 스프레드시트에 레시피마다 한 줄을 둔다(요리 이름, 요리 종류, 주재료, 세부 재료, 조리법, 난이도, 상황, 채널, 영상 주소, 저장한 날, 계량 도구, 문서 링크). 권한은 `drive.file`(처리기가 만든 파일만 만질 수 있음)이다. 스프레드시트 API가 이 권한으로 처리기가 만든 시트를 고칠 수 있는지는 확인 필요다. 안 되면 목록을 CSV로 올린다. 처리기용 Google Cloud 프로젝트에 OAuth 클라이언트(데스크톱 앱)를 만들고, 사용자가 한 번 로그인해 허락한다. A6에 따라 앱 상태를 정한다.
- **옵시디언:** iCloud 옵시디언 폴더에 새 보관함 `레시피`를 만들고(사용자) 같은 폴더 구조로 마크다운 파일을 쓴다. 분류·출처·날짜는 파일 머리 속성(YAML)으로 넣어 옵시디언에서 걸러 볼 수 있게 한다. 아이폰 옵시디언에는 iCloud로 저절로 나타난다.
- 무엇을 어디에 썼는지(드라이브 파일 id, 옵시디언 경로, 쓴 시각)는 DB에 남겨 다시 쓰기·옮기기에 쓴다.
- 사본은 맥 주인의 계정(구글 계정, Apple ID)에 쓴다. 배우자는 앱에서 본다. 배우자도 드라이브 사본을 보고 싶으면 드라이브에서 `레시피` 폴더를 직접 공유하면 된다(처리기가 공유하지 않는다). iCloud 옵시디언 보관함은 그 Apple ID 기기에만 보인다.

- **레시피북:** 맨 위 담기 칸, 그 아래 처리 중·대기·실패(진행 단계 글과 "다시 하기"), "확인 필요 N", "가진 재료" 화면으로 가는 길, 거르기(요리 종류, 주재료, 조리법, 난이도, 상황, 즐겨찾기, 지금 만들 수 있음, 1~2개만 사면 됨), 찾기(이름·재료). 처리 상태는 Realtime으로 바로 바뀌고, 앱이 다시 보일 때 새로 읽는다(아이폰 홈 화면 앱은 연결이 끊긴다).
- **진행 단계 글:** "영상 정보 받는 중", "자막 받는 중", "말 받아쓰는 중", "화면 글자 읽는 중", "레시피 정리 중", "다시 읽어 맞춰 보는 중", "저장 중". "AI", "분석 중" 같은 말은 쓰지 않는다.
- **상세:** 출처 영상(썸네일 없이 제목·채널·길이, 누르면 유튜브), 분류와 난이도 근거, 계량 도구, 인분 바꾸기(1~8인분), 재료(묶음별, 원래 표기, 출처 표시 "설명란" / "말 4:02" / "화면 0:14"를 누르면 그 장면, 덧붙인 분량은 "덧붙임"으로 따로, 있음·없음 표시), "가진 재료 9/14"와 "모자란 재료 장보기에 담기", 순서(불 세기, 넘어가는 신호, ▶ 시각, 용어는 밑줄 → 풀이), 원리, 다른 곳, 고친 곳(하나씩 "되돌리기"), 우리 집 메모·별점·즐겨찾기, 고치기.
- **확인:** 확인 필요를 하나씩 보인다. 까닭, 후보 값(출처·시각), ▶ 그 장면, "이 값", "직접 고치기". 다 보면 "확인을 마침". 사람이 고른 값의 출처는 `user`다.
- **요리 화면:** 휴대폰 기준(11번). 큰 글씨, 한 단계씩 넘기기, 단계에서 쓰는 재료와 분량(고른 인분 배수 반영), 넘어가는 신호, 타이머(출처에 시간이 있을 때만), 재료 체크, 끝에 "다 쓴 재료 끄기".
- **가진 재료:** 늘 있음·지금 있음 두 묶음, 사전에서 찾아 더하기, 끄기. 맨 위에 "장보기에서 산 것 N개를 넣을까요?". 화면 꺼짐 방지는 Screen Wake Lock으로 한다. 아이폰 홈 화면 앱에서 되는지는 확인 필요다.
- **고치기:** 재료·단계·분류를 고칠 수 있다. 고친 값은 출처 `user`다.

## 9. 데이터

### DB (`recipe` 스키마, `docs/recipes/contract/db-draft.sql`에서 출발)

- 마이그레이션 이름은 `<가장 늦은 파일보다 뒤 시각>_recipe_<주제>.sql`. 2026-11-19 기준 가장 늦은 파일은 `20261121000000_refunds.sql`이다.
- 첫 판의 표: `recipes`, `ingredients`, `steps`, `inbox`, `ingredient_dict`, `pantry`, 처리기 상태, 보관 기록. 함수 `import_recipe()`, `cookable()`.
- 초안에서 바꾸는 것:
  - `recipes.status`: `review`(확인 필요 있음) / `saved` / `archived`. 초안의 `draft`를 바꾼다.
  - 덧붙임 칸(`servings_suggested`, `ingredients.suggested_*`, `steps.editor_tip`)은 그대로 둔다(22번). 출처 값에서 `secondary`, `page`를 뺀다(첫 판에서 안 씀). `editor`는 덧붙임 칸의 출처로만 쓴다.
  - 요리 종류 낱말을 다섯(한식, 양식, 일식, 중식, 기타)으로 줄이고, 난이도(`difficulty`: 쉬움·보통·어려움)와 그 근거(재료 수, 단계 수, 손 많이 가는 조리법), 용어 풀이(`glossary`: 말, 풀이, 출처, 시각)를 더한다.
  - `pantry`: 초안 그대로(지금 있음·늘 있음, 어디서 알았는지). 장보기에서 넣은 것은 출처를 `grocery`로 적는다.
  - `ingredient_dict`: 처리기가 새 항목(`added`)을 넣을 수 있게 `recipe-worker`(서비스 롤)가 쓴다. 앱은 읽기만.
  - 더하는 것: 재료의 근거 시각(`at_seconds`), 레시피의 계량 도구와 그 근거, 세부 재료(`main_details`), 고친 곳(`corrections`), 확인 필요(`review_items`). `review_count`는 `review_items`에서 세는 트리거로 둔다(앱에서 고쳐도 맞게).
  - `inbox`: 주소, 출처 열쇠, 상태(`waiting`/`processing`/`done`/`failed`), 진행 단계, 가져간 시각, 마지막 진행 알림, 시도 횟수, 실패 까닭, 만든 레시피. 같은 가구에서 같은 출처의 대기·처리 중 줄은 하나만.
  - 처리기 상태(마지막 확인 시각, 버전): 서비스 롤만 쓰고 구성원은 읽는다.
  - 보관 기록(레시피별 드라이브 파일 id, 옵시디언 경로, 쓴 시각): 서비스 롤만 쓰고 구성원은 읽는다.
- RLS: 가구 구성원만 읽고 쓴다(`private.is_household_member`). 앱이 고치는 칸은 칸마다 `grant update`를 준다(빠지면 고치기 전체가 권한 오류로 실패한다).
- 등록은 `recipe.import_recipe()` 하나로만 한다. `recipe-worker`가 서비스 롤로 부르고, 넣는 사람은 그 주소를 담은 구성원이다.
- 앱이 `recipe` 스키마를 읽으려면 Supabase 대시보드의 "Exposed schemas"에 `recipe`를 더해야 한다(장보기 때와 같음, 사용자).
- 경계: 레시피 마이그레이션은 `recipe` 스키마만 만들고 바꾼다. `public`은 참조·읽기만, `grocery`는 건드리지 않는다. `tests/grocery/boundary.test.ts`는 `_grocery_` 파일만 보므로 `_recipe_` 파일을 보는 검사를 `tests/recipes/`에 둔다. PGlite 시험 틀(`tests/grocery/dbSetup.ts`)도 `_recipe_` 파일 앞에 가구·구성원을 만들 수 있게 고친다.

### 계약 v2 (`docs/recipes/contract/recipe.schema.json`)

v1에서 위 DB 변경과 같이 바꾼다. 근거 시각·계량 도구·세부 재료·난이도·용어 풀이·고친 곳·확인 필요 더하기, 요리 종류 다섯으로 줄이기, 출처 값 줄이기. 덧붙임 칸은 v1 그대로 둔다. 기준 답안(`contract/examples/youtube-AkX6uA4BaDs.json`)도 v2로 고치고 영상 길이를 793초로 바로잡는다(실제 값). 앱(zod), 처리기, `recipe-worker`가 같은 검사 코드를 쓴다.

## 10. 서버 함수 `recipe-worker`

- `verify_jwt = false`(`supabase/config.toml`에 더함). 부르는 쪽 확인은 `event-reminders`와 같은 방식이다. 헤더 `x-recipe-worker-secret`을 서버 환경변수 `RECIPE_WORKER_SECRET`과 시간 일정 비교(SHA-256 뒤 비교)로 맞춘다. 맞지 않으면 401.
- 서비스 롤 키는 서버에만 있다. 처리기는 비밀 문자열 하나만 가진다. 이 문자열이 새면 남이 대기 중인 주소를 보고 레시피를 넣을 수 있지만, 가계부 내역이나 다른 표는 읽지 못한다. 요청 크기와 횟수에 한도를 둔다.
- 하는 일:
  - 일 받기: 대기 중인 일 하나를 처리 중으로 바꿔 돌려준다(가져간 시각이 3분 넘게 끊긴 처리 중 일도 다시 줌).
  - 진행 알림: 단계 글, 마지막 진행 알림 시각.
  - 결과 넣기: 계약 v2 검사 → `import_recipe` → 대기 줄을 끝냄.
  - 실패 알리기: 까닭.
  - 보낼 것 묻기: 확인을 마쳤고 마지막으로 쓴 뒤 바뀐 레시피의 내용.
  - 보낸 것 적기: 파일 id, 경로, 시각.
  - 살아 있음 알리기.
- 맥이 사람 없이 Claude를 돌리는 길이 안 될 때(A2)는 이 함수에 "정리하기"를 더해 서버에 둔 Anthropic 키로 정리한다.

## 11. 보안과 개인정보

- 영상, 소리, 장면 그림, 자막·받아쓰기 원문은 저장소, DB, 드라이브, 옵시디언 어디에도 넣지 않는다. 남기는 것은 다시 쓴 글, 숫자, 출처, 영상 시각뿐이다(P-06). 작업 폴더는 일이 끝나면 지운다.
- 설명란·자막·화면 글자는 믿지 않는 입력이다. 영상 속 글이 Claude에게 무엇을 시켜도 할 수 있는 일이 없게, `claude -p`에는 작업 폴더 읽기만 허락한다. 결과는 계약으로 검사만 하고, 결과를 명령으로 실행하지 않는다.
- 드라이브 권한은 `drive.file`만 쓴다. 처리기가 만든 파일 밖은 못 본다.
- 이 저장소는 공개다. 보관함 이름, Google 프로젝트 id, 계정, 집 위치를 문서·코드에 적지 않는다.
- CLAUDE.md의 레시피 부분(지금 초안)을 고친다: 작업 파일 위치(`~/Library/Caches/recipe-worker/`, 손 시험은 `.recipe-cache/`), `recipe-worker` 함수, 마이그레이션 경계, 처리기 비밀 위치.

## 12. 시험

- 단위 시험: 주소 정규화, 숫자 찾기(한국어 수, 분수, T·t), 단위 검사, 계약 v2 검사, 분류 낱말, 난이도 규칙, 고친 곳·확인 필요 만들기, 다른 곳 짝짓기, 인분 바꾸기(1~8인분, 기준이 덧붙인 인분일 때 표시, 반올림, 약간·덧붙임 표시 유지), 사전 맞추기, 장보기 분류 짝.
- DB(PGlite): RLS(다른 가구는 레시피·재료·가진 재료·`cookable` 결과를 하나도 못 봄), 담기 권한, 일 받기와 3분 끊김 뒤 다시 가져가기, `import_recipe`, `review_count` 트리거, 덧붙임이 출처 숫자 칸에 못 들어감, `cookable`(없어도 되는 재료·늘 있음 제외), 경계 검사(레시피 마이그레이션이 `grocery`·`public`을 바꾸지 않음).
- `recipe-worker`: 비밀 틀림 401, 계약에 안 맞는 결과 거절.
- 처리기: 근거 묶음 시험 자료로 정리·검증 흐름. 공개 저장소이므로 실제 자막을 넣지 않고 만든 자료를 쓴다.
- 끝까지 한 번: 기준 답안 영상(재료 숫자 15개, 대파·깻잎 나눠 넣기, 다른 곳 세 군데, 단계 시각 ±15초), 간장두부조림(19분 29초, 걸린 시간), 설명란에 분량이 있는 쇼츠(`FgKy9Xq4LKY`), 설명란이 빈 쇼츠(`wruh__UmGaU`). 세는 것: 맞힌 숫자, 빠뜨린 숫자, 어느 출처에도 없는 숫자(0이어야 함).
- 화면: `npm run screens`로 390·1280px, 라이트·다크. 탭 줄 7칸을 본다.

## 13. 사용자가 할 일

- 설치 허락: yt-dlp, Deno, whisper.cpp 한국어 모델(약 1.6GB, 확인 필요), `/watch`(예비). ffmpeg·whisper.cpp는 이미 있고 글자 인식은 macOS에 들어 있다.
- Supabase 대시보드: Exposed schemas에 `recipe` 더하기. 서버 환경변수 `RECIPE_WORKER_SECRET` 넣기(값은 Claude가 맥에서 만들어 파일로 건넨다).
- 구글: 처리기용 OAuth에 한 번 로그인하고 허락하기.
- 옵시디언: iCloud에 새 보관함 `레시피` 만들기.
- macOS가 처리기에 폴더 접근을 물으면 허락하기(A5).
- PC 브라우저에서 앱에 로그인해 두기(북마크).
- 마이그레이션 적용과 main 배포 허락(저장소 규칙).
