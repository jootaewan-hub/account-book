## 3. 어떻게

### 3-1. 주유

**읽기(`supabase/functions/extract-entries/extract.ts`)** — `EntrySchema`에 `fuel`을 더한다.

```
fuel: { liters: number|null, price_per_liter: number|null, fuel_type: string|null } | null
```

프롬프트 규칙: "주유소 영수증이면 fuel에 유종(휘발유·경유·고급휘발유·LPG 등 영수증 표기 그대로), 주유량(리터, 소수 셋째 자리까지), 리터당 단가(원)를 적는다. 단가 × 주유량이 결제 금액과 거의 같아야 한다. 보이지 않는 값은 null. 주유 영수증의 items는 비워 둔다. 주유가 아니면 fuel은 null." 분류 목록에 `차량·주유`가 있으면 category도 그것으로.

정리(`checkFuel`, 순수 함수·시험): 리터는 0 초과 500 미만, 단가는 100 초과 100,000 미만 정수만 받는다. 둘 중 하나라도 없으면 그 값은 null로 두고 화면에서 적게 한다(계산해 채우지 않는다). 단가 × 리터와 결제 금액이 1% 넘게 다르면 `fuel_note`에 "단가 × 주유량 N원이 결제 금액과 M원 달라요" 문장을 넣어 확인 화면 경고로 보인다.

**초안(`src/lib/smart.ts`)** — `Draft.fuel: { liters, price_per_liter, fuel_type } | null`. 주유 내역의 분류는 `차량·주유`가 있으면 그것(없으면 기존 규칙). 할부·나누기와는 무관하다(주유는 상품 줄이 없어 나뉘지 않는다).

**확인 화면(`SmartSheet` → `DraftCard`)** — `fuel`이 있는 초안에 "주유" 칸: 유종(글자), 주유량 L(소수 셋째 자리까지), 리터당 원(정수) 입력 세 개와 "단가 × 주유량 = N원" 줄. 값이 비어 있으면 그 칸을 비워 두고 저장할 수 있다(그때는 주유 기록을 저장하지 않고 내역만 저장, 안내 문장). 지난 주유가 있으면 "지난 주유(10월 2일, 휘발유) 1,629원/L보다 ▲ 23원" 한 줄(같은 유종끼리만, 등락 표기는 D-012 규칙: ▲ `clay`, ▼ `indigo`, 같으면 "같아요").

**저장(`saveDraft`)** — 내역을 넣은 뒤 리터와 단가가 둘 다 있을 때만 `fuel_fills`에 한 줄 넣는다(`transaction_id`, `liters`, `price_per_liter`, `fuel_type`; 유종은 없어도 된다). 주유 저장이 실패해도 내역은 되돌리지 않고 "주유 기록은 저장하지 못했어요"를 알린다(장보기 연결 실패와 같은 방식).

**저장 뒤 보기** — 달·내역 목록을 읽을 때 `fuel_fills(liters, price_per_liter, fuel_type)`를 함께 읽어(`Transaction.fuel`) 내역 행의 보조 줄과 수정 시트에 "휘발유 35.2L, 1,652원/L"로 보여 준다(읽기 전용). 유종 비교("같은 유종끼리")는 저장은 영수증 표기 그대로 두고 견줄 때만 휘발유·고급휘발유·경유·LPG로 정규화한다(`fuelKind`).

**표(`supabase/migrations/20261031000000_fuel_fills.sql`, public)** —

```
public.fuel_fills (
  id uuid pk, household_id uuid → households cascade,
  transaction_id uuid not null unique, (transaction_id, household_id) → transactions (id, household_id) on delete cascade,
  liters numeric(7,3) check (> 0 and < 1000), price_per_liter integer check (> 0 and < 100000),
  fuel_type text check (char_length <= 20), created_by uuid default auth.uid(), created_at timestamptz
)
```

RLS는 `utility_bills`와 같다(가구 구성원만 전부). 날짜·금액·가게 이름은 따로 두지 않고 내역에서 읽는다(`select('…, transactions(occurred_on, amount, title)')`). 내역을 고치면 그대로 따라오고, 지우면 함께 지워진다. 실시간 목록에는 넣지 않는다(통계 탭이 내역이 바뀔 때 다시 읽는다). `tests/db.test.ts`에 RLS(다른 가구 못 봄·못 넣음)·연쇄 삭제·제약 시험.

**계산(`src/lib/fuel.ts`, 순수 함수·시험)** —

- `fuelFacts(fills, today)`: 최근 주유(날짜·가게·유종·L·원/L·금액), 지난 같은 유종 주유와의 리터당 차이, 이번 달·지난달(횟수·L·금액), 평균 주유 간격(최근 6번의 날짜 간격 평균, 2번 미만이면 null), 100km당 같은 연비는 **계산하지 않는다**(주행거리를 모른다).
- `fuelTrend(fills, n = 12)`: 최근 n번의 (날짜, 원/L, L, 유종). 유종이 섞이면 가장 최근 유종만 선으로 그리고 다른 유종은 점으로(빌더가 더 단순하게 해도 된다 [빌더]).

**통계 탭 "주유" 묶음(`src/components/FuelCard.tsx`)** — 관리비 묶음(`BillCard`) 다음에 둔다. 큰 숫자 하나(최근 리터당 가격)와 그 옆에 날짜·가게·유종, 지난번 대비 한 줄, "이번 주유 35.2L, 58,150원", 리터당 가격 선 그래프(최근 12번, 첫 값·마지막 값·최저·최고를 글자로 직접, 축 숫자는 `man`이 아니라 원 그대로), 이번 달·지난달 두 줄, 평균 간격 한 줄, 최근 주유 목록(최대 8줄: 날짜, 유종, L, 원/L, 금액). 빈 상태: "주유소 영수증을 찍어 넣으면 리터당 가격 변동과 주유량을 모아 보여 드려요." 묶음 아래 "주유 영수증 넣기" 버튼(영수증 입력을 연다).

### 3-2. 장보기 비교

**읽어 오는 것(`src/lib/api.ts`)** — `fetchItemHistory(householdId, from)`: `occurred_on >= from`(오늘 − 365일)이고 품목 줄이 있는 지출 내역(`transaction_items!inner`)을 id·날짜·제목·플랫폼·분류·created_at·품목 줄과 함께, 최근 날짜부터 1,000건까지(PostgREST 기본 한도). 확인 화면이 `review` 단계로 들어갈 때 한 번 읽는다(장보기 품목을 읽는 `useEffect`와 같은 자리). 못 읽어도 입력은 그대로 된다.

**계산(`src/lib/shopCompare.ts`, 순수 함수·시험)** —

1. 이름 맞추기. `normName`: 공백·기호(★*·,()[]/)·대소문자를 없앤다. 두 줄이 같은 상품인지는 (a) 정규화한 이름이 같거나 한쪽이 다른 쪽을 포함(짧은 쪽 4자 이상) → "같은 상품", (b) 단어(공백으로 나누고 용량·수량 토큰과 국산·특가 같은 꾸밈말을 뺀 2자 이상)가 2개 이상 겹침 → "같은 상품", (c) 이 줄이 연결(체크)된 장보기 품목 이름(예 "된장")이 지난 줄 이름에 들어 있음 → "같은 품목"(다른 상품일 수 있음). (a)(b)를 먼저 보고 없으면 (c). 같은 등급이면 가장 최근 것.
2. 값 비교. 둘 다 용량(`pack_size`·`pack_unit`)이 있고 단위가 같으면 100g·100ml·1개당 값으로, 아니면 개당 가격(`unit_price`, 없으면 금액 ÷ 수량)으로. 차이와 비율(`pctChange`)을 내고, 지난 줄의 날짜·가게(내역 제목 또는 플랫폼)·상품명·값을 함께 낸다. "같은 품목" 등급은 용량 값이 있을 때만 비교한다(개당 가격은 크기가 달라 뜻이 없다).
3. 최근에 또 산 것. 같은 상품·같은 품목의 지난 구매가 있고, 그 뒤 지난 날수가 기준보다 짧으면 표시. 기준은 같은 상품의 지난 구매가 2번 이상이면 그 간격 중앙값의 절반, 아니면 품목 종류 표(`RESTOCK_DAYS`, **추측입니다**): 장류·소스·기름·설탕·소금·조미료·잼·케찹·마요네즈·식초·미림·참치액·참깨 45일, 라면·과자·시리얼·그래놀라·커피 10일, 우유·요거트·두부·계란·샐러드·치즈·버터·햄 5일, 채소·과일·정육·수산 3일, 그 밖 7일. 문장은 사실만: "10일 전(10월 11일)에도 샀어요 — 청정원 순창 재래식 생된장 500g, 이마트". 표 값이 맞지 않으면 사용자가 알려 주고 고친다.
4. 장보기 목록에 없던 것. 영수증 상품 줄 중 장보기 품목과 맞춰지지 않은(체크도 제안도 없는) 것. 이 영수증에서 맞춰진 줄이 하나도 없으면 이 항목을 내지 않는다(목록을 안 쓴 날은 전부 '없던 것'이라 뜻이 없다).
5. 같은 것이 두 줄: 한 영수증 안에서 정규화한 이름이 같은 줄.
6. 처음 사는 것: 1의 어느 등급으로도 못 맞춘 줄(접힘).
7. 지난 장보기. 과거 내역을 "장보기 한 번"으로 묶는다: 같은 날짜이고 `created_at`이 5분 안에 이어지는 내역들을 한 묶음으로(상품별로 나눠 저장한 영수증도 한 번으로 보인다), 상품 줄 합이 3개 이상이고 내역 하나라도 분류가 `장보기`·`식비`인 묶음만(쿠팡 가전 주문·식당 영수증은 빠진다. 빌더 검토 반영). 가장 최근 묶음을 "지난 장보기"로 보고 합계·개수를 이번 것과 견준다. 가게는 묶음 안 내역의 플랫폼이나 제목이 상품명이 아닌 것(품목 줄 2개 이상인 내역의 제목), 없으면 "장보기".

**화면(`src/components/ShopCompareCard.tsx`)** — 영수증·쇼핑 캡처 확인 화면에서 "장보기"로 보는 묶음(초안 분류가 `장보기`·`식비`이거나 상품 줄이 장보기 품목과 맞춰짐)마다 하나, 그 묶음의 초안 카드들 아래·장보기 연결 묶음 위. 제목 "이번 장보기 살펴보기". 분류 칩을 바꾸면 따라 뜨거나 사라진다.


- 각 묶음은 다섯 줄까지 보이고 "N개 더 보기"로 편다. 비싸진 것은 차이 큰 순, 싸진 것도 차이 큰 순.
- 등락 표기는 D-012와 같다(▲ `clay`, ▼ `indigo`, 글자와 함께). 비율은 우리 기록끼리의 계산이라 낸다(외부 시세가 아니다).
- 지난 기록이 하나도 없으면 묶음은 "지난 장보기 기록이 없어요. 다음 장보기부터 견줘 드려요." 한 문장과 "장보기 목록에 없던 것"만.

### 3-3. 오늘 기록 문제를 줄이는 작은 수정(`extract-entries`)

- `index.ts`: 품목 합계가 안 맞아 Sonnet으로 다시 읽었는데 둘 다 안 맞으면 지금은 Haiku 결과를 쓴다 → Sonnet 결과를 쓴다(더 큰 모델이 이름을 덜 틀린다. 비용은 이미 든 것).
- 프롬프트: "영수증의 원단위 절사·끝전 할인·봉투값도 줄로 넣는다(절사·할인은 음수 금액, is_product false)". 합계가 맞으면 다시 읽기도 줄어든다.
- 둘 다 시험 가능한 범위에서 시험(프롬프트 문장 포함 여부, 선택 규칙은 함수로 떼어 시험).

### 3-4. 바꾸지 않는 것

- 장보기 탭 화면·`grocery` 스키마. 이번 범위는 가계부(`public`, `src/lib`, `src/components`)와 `extract-entries`뿐이다. `tests/grocery/boundary.test.ts`는 새 마이그레이션 이름에 `_grocery_`가 없으므로 대상이 아니다.
- 주유를 직접 입력(사진 없이)하는 칸과 저장 뒤 리터·단가를 고치는 칸. 다음에 필요하면 더한다(수정 시트에 세 칸을 두고 `fuel_fills`를 update).
- 오늘 저장된 기록의 수정(이름 오독·가맹점 이름). 사용자가 내역 수정으로 고친다.

## 4. 범위 밖(비목표)

- 오피넷 등 외부 유가와 비교, 연비(주행거리 없음), 차량 여러 대 구분.
- 저장한 뒤 지난 장보기 비교를 다시 보는 화면, 통계 탭의 장보기 묶음.
- "안 사도 된다"는 판단 자체. 사실만 보여 준다.
- 영수증 이름 오독을 모델 바꿈 없이 고치는 것(3-3의 작은 수정만).

## 5. 실패 조건

- 화면에 출처 없는 숫자가 나온다(리터·단가는 영수증 값, 비교 값은 우리 기록의 날짜·가게와 함께).
- 주유 저장이 실패했는데 사용자가 모른다. 내역 삭제 뒤 주유 기록이 남는다.
- 다른 가구의 주유·품목 기록이 보인다(RLS).
- 장보기 비교가 느려 확인 화면이 늦게 뜬다(기록 읽기는 분석과 무관하게 뒤에서, 못 읽어도 저장은 됨).
- 장보기 CSS 규칙(`.grocery` 안에서만)을 깬다. 새 클래스는 가계부 쪽(`src/styles.css`)이고 `tests/grocery/tokens.test.ts`가 검사한다.

## 6. 빌더에게 맡기는 것

- 그래프 구현(SVG 선 하나). 유종이 섞일 때의 표현.
- 확인 화면 주유 칸의 입력 검증 문구.
- 이름 맞추기의 꾸밈말 목록·크기 토큰 정규식(장보기 `grocery.name_tokens`와 `_shared/fit.ts`의 `SIZE_RE`를 참고).
- 캡처 장면 이름과 셸 가짜 데이터(과거 영수증 두 번, 주유 세 번).

## 7. 운영 반영 순서(사용자 확인 뒤)

1. 공유 DB에 `apply_migration`(`fuel_fills`) → Advisors 확인.
2. `extract-entries` 배포(verify_jwt true 그대로).
3. main 병합·푸시(GitHub Pages).
4. 사용자: 주유 영수증 1장, 장보기 영수증 1장으로 실제 확인. 이름 오독이 여전하면 긴 영수증은 Sonnet으로 처음부터 읽을지 정한다.
